# APT-SIGNAL 시스템 인수인계 (apthub 클라우드 방 → 다른 방)

작성 2026-11-06 · 작성자 apthub 클라우드 세션(`apthub-d1`) · 기준 커밋 `d7083b9`

APT-SIGNAL 작업이 여러 방에 흩어져 있어, 이 방이 가진 시스템 전체를 한 문서로 넘긴다.
다른 방이 이걸 읽고 **중복 구축을 피하거나 병합을 판단**할 수 있게 쓴다.
읽는 쪽 시스템 설명을 이 문서 아래 `## 상대 방 시스템` 절에 붙여 주면 병합 검토를 이어갈 수 있다.

> 이 방은 클라우드 세션이라 맥에서 도는 다른 방에 메시지를 보낼 수 없다(Remote Control 미연결).
> 교환 채널은 이 레포뿐이다.

## 1. 정체

| | |
|---|---|
| 무엇 | 수도권(서울·경기·인천) 부동산 정책·시장 동향 모니터링 대시보드 |
| 레포 | `github.com/piko9388/apthub` (**public**) |
| 배포 | GitHub Pages, `main` push 시 자동 (`.github/workflows/pages.yml`) |
| 산출물 | 단일 파일 `index.html` (약 1.1MB, 데이터 인라인) |
| 1차 독자 | 소유자 본인의 의사결정 도구. 공개는 부산물 |
| 홈의 질문 | "지난주 무슨 일이 있었나" (변화 중심) |

## 2. 코드 구조

```
scripts/build_site.py        정적 사이트 생성기 — Python 데이터층 + 인라인 HTML/CSS/JS 템플릿
scripts/apthub_official_apis.py  공식 API 수집기 (RTMS·ECOS·LH·K-apt·KOSIS)
scripts/healthcheck.py       데이터 신선도 점검 (트랙 + 지표별)
src/apthub/                  패키지 — schema / filters / store / manual / report / config
  schema.py    Signal 데이터클래스, id 생성, 날짜 정규화
  filters.py   enrich — 지역·분류·트리거 자동 태깅
  store.py     날짜별 파일 저장소 (id 중복 시 나중 쓰기가 이김)
data/seed/*.json             신호 원본 (로더가 글롭으로 전부 읽음)
data/complex/*.json          단지 카탈로그 (일반 25 + LH 임대 669)
config/                      지역·모니터링 규칙 정의
tests/test_pipeline.py       24개
```

## 3. 데이터 모델 — 두 트랙

- **뉴스(`kind: news`)** — 기사·실거래 등 정성 신호. 지역·분류·트리거 자동 태깅.
- **지표(`kind: data`)** — 정량 지표. `metric/value/unit/sido/date` 필수.

지표 28종은 상위 **4축**으로 계통화해 표시한다.

| 축 | 뜻 | 지표 |
|---|---|---|
| 💰 자금 | 돈줄 | 기준금리·COFIX·주담대금리·가계대출증감·스트레스DSR |
| 📈 가격 | 값 | 주간 매매/전세변동률·부동산원 지수·KB매매변동률·평당가·5분위 평균매매가/배율·PIR·전세가율 |
| 🏗 수급 | 물량 | 미분양·준공후미분양·입주물량·분양가·공공임대 세대수/단지수·아파트세대수·공공임대비율 |
| 🔥 수요·심리 | 기세 | 주택/아파트 매매거래량·경매낙찰가율·청약경쟁률·매매전망지수·매수우위지수 |

축 머리에 `▲n ▼n →n`(계열별 최신값 대비 직전값)을 표기하되 **극성 합산은 하지 않는다** —
미분양 ▲는 약세, 거래량 ▲는 강세라 합치면 오독이 된다.

## 4. 파이프라인

```
수집(주간 cron)  →  data/seed/*.json  →  load_all()  →  normalize_signals()  →  build()  →  index.html  →  Pages
  RTMS·ECOS·LH·K-apt      글롭 전체 읽기    오염·단위 정규화    4축 렌더
```

- `.github/workflows/crawl.yml` — 매주 월 06:00 KST. 키 없으면 경고만 남기고 건너뜀.
- `.github/workflows/pages.yml` — `main` push에 `data/seed/**`, `data/complex/**`, `scripts/build_site.py`, `src/**`, `config/**` 변경 시 재배포.
- 키는 전부 레포 Secrets → env: `RTMS_KEY` `ECOS_KEY` `LH_KEY` `KAPT_KEY` `KOSIS_KEY` `KAPT_STD_UDDI`.

## 5. 깨면 안 되는 규칙

1. **PII 게이트** — `APTHUB_PUBLIC=1` 빌드는 개인 재무 정보를 제외한다. 공개 배포는 반드시 이 플래그. 검증: 빌드 후 `희주`/`희망#` 각 0건.
2. **키는 코드·시드에 절대 넣지 않는다.** env/Secrets만. 수집기는 플레이스홀더 키면 호출 전 중단한다.
3. **빌드는 결정적이어야 한다.** 같은 입력 → 같은 `index.html` (md5 일치). 과거 지역 태깅이 `set` 순회에 의존해 빌드마다 66건이 요동쳤다. 회귀 테스트가 `PYTHONHASHSEED`를 달리한 서브프로세스로 검사한다.
4. **날조 금지.** URL은 실재 링크, 환산·해석값은 `○추정` 표기. 발표 일정 같은 미래 날짜를 하드코딩하지 않는다 — 주기는 데이터에서 실측한다.
5. **main 직접 push 금지.** PR 경유.

## 8. 병합 검토 시 볼 곳

다른 방과 겹칠 가능성이 높은 순서대로.

1. **데이터 소스** — 그쪽이 이미 뚫어둔 수집 경로가 있으면 위 열린항목 1이 바로 풀린다. 이 방의 최대 병목이다.
2. **신호 스키마** — 이쪽은 `Signal`(id/date/title/summary/source/url/category/sido/region/trigger/kind/metric/value/unit). 필드가 다르면 매핑표가 필요하다.
3. **산출물 형태** — 이쪽은 단일 HTML 정적 배포. 브리핑·리포트·인스타 등 다른 산출물이 있으면 같은 신호 풀을 공유할 수 있다.
4. **자동화 스케줄** — 양쪽 cron이 같은 API를 중복 호출하면 쿼터를 깎는다(K-apt 기본정보는 일 1만 한도).
5. **소유권** — `부동산 동향 코드방과 이방 차이` 방에 "APT-SIGNAL 소유를 부동산 방으로 넘길지"가 미결로 걸려 있다. 병합 전에 이것부터 정해야 작업이 또 갈라지지 않는다.
